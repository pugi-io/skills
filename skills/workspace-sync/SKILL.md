# Workspace synchronization

Run the requested workspace maintenance end to end. Prioritize evidence from the latest 48–72 hours while checking older unresolved work. This is a recency priority, never a cutoff: for every assigned unresolved Jira issue, inspect relevant status/comment history and linked PR, merge and deployment evidence across at least the prior three weeks (extend farther when the issue or linked work is older). A fix may have been completed weeks before its latest status update or staging deployment. Recheck live state before every mutation and distinguish current observations from historical notes or plans.

## What works today

| Step | Surface | Status |
|---|---|---|
| Inspect and safely fast-forward Git checkouts | Git CLI and configured remotes | Available when the checkout and network permit it |
| Inspect and update the user's open PRs | GitHub CLI or connected GitHub integration | Available when authenticated access is present |
| Review assigned Jira work | Connected Jira integration | Available when the Jira connection is present |
| Reconcile workspace docs and Graphify | Workspace files and configured Graphify tooling | Available when the configured sources can be read |
| Resolve an unambiguous merge conflict | Isolated checkout, source/history and focused checks | Available when evidence identifies one safe behavior |

## Workflow

1. **Inventory and Git.** Recursively find Git repositories, including worktree `.git` files, without entering dependency caches or generated outputs. Deduplicate linked worktrees by common Git directory while recording every worktree path and status. For each repo, record remotes/default branch, branch/upstream, ahead/behind, staged/unstaged/untracked/ignored changes, unmerged paths, in-progress operations and every stash. Fetch all configured remotes with `git fetch --all --prune`. Pull only a clean checked-out base using `--ff-only`; never switch or pull a dirty feature checkout. If the user explicitly requests updating a dirty checkout, first save staged, unstaged, untracked, and relevant ignored data in independently restorable backups; record hashes/manifests and verify restoration paths. Use a uniquely named recovery stash only after those backups exist. Restore the original staged/unstaged state and compare tracked and untracked content byte-for-byte before dropping that newly created recovery stash. Never pop/drop/clear pre-existing stashes as part of this procedure. If any backup or comparison is incomplete, retain the stash and stop modifying that checkout.
2. **Resolve conflicts autonomously when evidence supports one answer.** Check both existing unmerged index entries and real merge conflicts against the fetched upstream/base. An ahead/behind count, same-path edit, dirty checkout or failed Git command alone is not proof of a content conflict. For each real conflict, preserve and inspect the base, ours and theirs before editing; use an isolated worktree/copy if the primary checkout is dirty or shared. Prefer a semantic merge that retains compatible changes from both sides. Determine intended behavior from the user's latest instruction, current contracts, call sites/consumers, commit history and focused tests; do not choose an entire side merely for convenience. If this evidence identifies one safe result, resolve it without asking. During an active merge, stage only the resolved paths needed to clear their unmerged index entries; never include unrelated staged files. Run focused checks and report the files, behavior kept and reason. If behavior remains ambiguous or the choice affects security, data integrity or incompatible product decisions, do not guess: leave only that merge untouched, explain the competing outcomes and continue independent work. Never force-push, hard-reset or stash user changes.
3. **GitHub PRs.** Find every open PR authored by the user in discovered repositories, including drafts and inactive PRs; paginate until the provider reports the final page. Record base/head SHAs and inspect mergeability, CI/checks, reviews, general and inline comments, and unresolved review threads. Compare the PR's recorded base SHA with the freshly fetched target branch; GitHub mergeability can describe a stale base. Use `git merge-tree` or an equivalent isolated comparison against the current base before declaring a conflict. Address actionable feedback on the user's PRs only. For a real conflict, merge the fetched current base into the PR branch (do not rebase or rewrite published history), resolve evidenced conflicts from both sides, run relevant checks, review the final diff and outgoing commit authors/trailers, then push to the same PR branch. When there is no conflict, do not create a merge commit only to refresh the base; record the stale SHA and verification scope. Keep draft state unless asked to change it. Update title/body/checklist only when stale; use real screenshots only for visible UI changes. After a push, reread the PR head, mergeability, checks and review threads; do not claim computed status before the provider reports it. Do not close or merge PRs.
4. **Jira.** Paginate through all assigned issues across statuses and sprints, then add issues linked to the user's PRs/commits. Paginate each issue's comments to `isLast=true`; record how many issues had comments and distinguish a latest-comment scan from a full history review. Inspect recent changes, comments, blockers, descriptions and links. Do not use an issue's `updated` date as a work-history cutoff: inspect linked PR/commit and deployment history at least three weeks back for each unresolved issue, including older merges and later deploys. Update only evidence-backed fields/comments. `Backlog` / `To Do` means work has not started; `In Progress` / `In Dev` means implementation or required review fixes remain. `In Review` means the full code implementation is complete and every associated implementation PR is merged. `Ready QA` is the handoff after code completion, merge of all associated implementation PRs and deployment of all required changes/dependencies to staging or production; record the exact target URL, deployed SHA/run and QA scenarios. It lets QA begin and is not acceptance. Production evidence is tracked separately. Preserve existing `Ready QA` and `Done` statuses unless the user explicitly asks otherwise. Do not change `Rejected By QA` without the user's explicit decision to start a new QA pass. If deployment evidence or its deployed SHA is missing, do not promote to `Ready QA`.
5. **Workspace documentation.** Update the established documentation outside Git repositories. Reconcile architecture, API, tasks, PR, Jira, roadmap, changelog and implementation against current primary evidence. Fix proven stale statements and duplicates while preserving meaningful decisions and dated history. Prefer existing documents over new top-level files.
6. **Graphify.** Inspect corpus configuration, output paths, ignore rules, refresh semantics and existing integrity before writing. Refresh the sources actually requested; code-only extraction does not update PR, Jira or document semantics. Preserve history and unrelated dirty files. Remove only confirmed obsolete temporary records. Verify IDs, edges, provenance, warnings and coverage, and state clearly which sources were unavailable or omitted.
7. **Verification and report.** Recheck Git status, fetched/upstream state, PR conflicts/checks/reviews/threads, Jira consistency, documentation and Graphify integrity. Report completed work, exact verification evidence, links to PR/Jira, and blockers separately. Never describe partial or unverified work as complete.

For a repeat run, refresh the full live inventory rather than copying the prior snapshot. Keep `docs/PULL-REQUEST-WORKFLOW.md` and `docs/GRAPHIFY-MAINTENANCE.md` concise current guides. Record dated Git/PR/Jira evidence in `docs/pr-drafts/2026-10-26-review-fixes/STATUS-REFRESH.md`; record detailed Graphify backup, candidate, coverage and integrity evidence in `docs/history/GRAPHIFY-MAINTENANCE-HISTORY-2026-11-18.md`. Keep reusable policy in this skill and avoid duplicating a run across several documents.

## Safety boundaries

- Preserve staged, unstaged, untracked, ignored user data and other worktrees.
- Never run `git reflog expire` (including `--all` or before `git gc`) without first saving every stash: the stash stack lives in the `refs/stash` reflog, and expiring it deletes all stash entries older than the tip. If reflog expiry already ran, recover `stash@{0}` from the surviving `refs/stash` ref by rewriting `.git/logs/refs/stash` (single line, `<zero> <sha> <ident> <ts> <tz>\t<message>`); older entries are usually unrecoverable after `gc --prune=now` (incident 2026-11-20).
- Treat conflict resolution as part of the requested sync when the user asks to resolve conflicts; do not stop at listing a resolvable conflict or ask the user to choose when repository evidence gives a safe answer.
- No force push, hard reset, mass deletion, PR merge/closure, or Jira closure.
- Do not bypass failed hooks without explicit authorization. The user's latest explicit instruction controls.
- If the current request explicitly requires `git push --no-verify`, inspect the effective hook configuration and determine which hooks that flag skips. Run available equivalent checks manually before the push and record unavailable or non-equivalent portions. Treat commit-time hooks separately: `git push --no-verify` does not itself authorize bypassing a failing commit hook. Do not infer skipped checks passed, and do not carry a one-task authorization forward as a default.
- Classify local check failures against the actual host and target runner before changing code. Preserve the failure log and distinguish a product/test failure from a host restriction, missing runtime, unsupported platform tool, or path allowlist; verify the intended platform in CI before reporting it passed.
- Networked changes to GitHub or Jira are permitted only within the scope of the user's current request and other applicable instructions. Do not send unrelated messages.
- A repeated run starts from live state, not the previous report. Reconcile old SHA/status notes against current GitHub/Jira/deployment evidence; preserve dated history while correcting current claims. If one repository or service is blocked, continue independent work and identify the blocked scope and cause.
